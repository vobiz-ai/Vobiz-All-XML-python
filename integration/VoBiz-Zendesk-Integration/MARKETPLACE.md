# Zendesk Marketplace submission

Tanishka asked Zendesk partner support how to submit this integration on
14 Sep 2026. Eric Shen replied on the 14th pointing at
[Submit your app](https://developer.zendesk.com/documentation/marketplace/publishing-to-the-marketplace/submit-your-app/).
This is that process, applied to this repository: what is already done, what is
outstanding, and the one thing that needs a product decision rather than code.

Last reviewed: **17 September 2026**.

---

## The decision that comes before any of this

**A Marketplace app cannot ask every customer to run their own Node backend on a
tunnel.** That is the single biggest gap between what is in this repository and
something Zendesk will approve.

The app holds no Vobiz credentials by design — they live in
`backend/`, which today is a local Express server behind cloudflared. For a
listing, one of these has to be true:

| Option | What it means | Effort |
|---|---|---|
| **Vobiz hosts it** (recommended) | One multi-tenant backend at a stable Vobiz domain. `backend_url` stops being a customer setting; the app points at Vobiz. Requires real per-account auth, not the single-account binding in `ISSUES.md` #2 | Highest, and the only one that reads as a product |
| Ship as an **integration app** (`marketingOnly: true`) | The listing is discoverable but not installable; it links to Vobiz-hosted setup. Legitimate, and much faster to list | Low |
| Keep it a **private app** | Customers upload the package themselves. No review, no listing | None — this is today |

Everything below assumes the first or second. Until that is chosen, submission
is blocked on product, not on engineering.

## Review timeline

- New app submissions: **1–3 weeks**
- Updates to an existing app: **1–2 weeks**
- Approved apps publish by **10am PST the next day**

## Checklist

### Account and org

- [ ] Register the organization at [apps.zendesk.com](https://apps.zendesk.com)
- [ ] Create the Marketplace profile (company details, support contact, logo)
- [ ] Request a **sponsored Zendesk Support account** to build and test against —
      Zendesk expects the app to be developed on one, not on a trial
- [ ] Note the **Organization ID** from the Organization page. It never changes
- [ ] Only for a paid listing: connect Stripe and record the Stripe Integration ID

### Manifest — **done**

| Requirement | State |
|---|---|
| `"private": false` | ✅ set |
| `defaultLocale` | ✅ `en` |
| `frameworkVersion` | ✅ `2.0` |
| `author` name/email/url | ✅ |
| `termsConditionsURL` | ⚠️ points at `https://vobiz.ai/terms` — **confirm that page exists** |
| `version` | ✅ `2.0.0` |

### Brand assets — **done**

Generated by `zendesk-app/tools/make-brand-assets.py` from the real Vobiz mark,
so they are reproducible rather than hand-exported:

| File | Spec | State |
|---|---|---|
| `assets/logo.png` | 320×320 PNG, no rounded corners | ✅ |
| `assets/logo-small.png` | 128×128 PNG-24, transparent, legible on light **and** dark | ✅ |
| `assets/icon_top_bar.svg` | SVG, monochrome, square, legible at 18×18 | ✅ — **the filename was wrong before** (`icon.svg`), so the top bar rendered no icon at all |

- [ ] `assets/screenshot-0.png`, `-1.png`, `-2.png` — **1024×768 PNG, full bleed,
      no padding, no rounded corners.** These must be real captures of the
      working panel and cannot be fabricated. Take them once the app is running
      against a live account: the dialer, an active call, and a logged ticket.

### Listing content — **done, needs a review pass**

`translations/en.json` now carries `short_description`, `long_description` and
`installation_instructions`. Read them once with a product hat on before
submitting — they are written to be accurate, not to be marketing copy.

- [ ] Choose up to **two** Marketplace categories
- [ ] Privacy policy URL
- [ ] Answer the mandatory compliance questions, including **disclosing what
      Zendesk data the app accesses**. For this app that is: ticket ID and
      requester name/phone (read), user search (read), ticket comments (write)

### Technical requirements

- [x] **Marketplace request headers** on external API requests —
      `X-Zendesk-Marketplace-Name`, `-Organization-Id`, `-App-Id`. Implemented in
      `backend/zendeskService.js`; the two IDs are env vars and stay blank until
      the app is accepted, at which point set `ZENDESK_MARKETPLACE_ORG_ID` and
      `ZENDESK_MARKETPLACE_APP_ID`. (ZAF's own `client.request` is exempt — this
      requirement is only for requests originating on our server.)
- [x] Third-party scripts pinned — JsSIP is `jssip@3.10.1`, not a floating `@3`
- [ ] **OAuth2 instead of an API token.** Zendesk "highly recommends" OAuth2 and
      expects a global OAuth client for Marketplace apps. The backend currently
      uses email + API token Basic auth. Reviewers do flag this
- [ ] Minimise API calls to avoid rate limiting — the app shares the customer's
      quota with every other integration they run
- [ ] `zcli apps:validate` passes with no errors (`zcli` is **not installed on
      this machine** — `npm install -g @zendesk/zcli` first)

### Submission

1. Go to `apps.zendesk.com/apps/new`
2. Consider a **Preview App** first — not published or discoverable, shared by
   direct link with named accounts. The right way to get this in front of a
   design partner before public review
3. Upload the ZIP from `zcli apps:package zendesk-app` (writes to `tmp/`).
   The portal validates it and flags errors in red (blocking) and warnings in
   yellow (non-blocking)
4. Optionally link the GitHub repository
5. Pick categories, add the privacy policy URL, answer compliance, accept T&Cs
6. Submit, then track it under the Submissions tab

## What to tell Eric

The useful follow-up questions, now that the docs have been read:

1. Confirm whether a **per-customer `backend_url` setting** is acceptable for a
   public app, or whether the backend must be vendor-hosted. This is the one
   thing that decides which of the three options above we take.
2. Confirm whether an **integration app** (`marketingOnly: true`) is the right
   listing type for a telephony product where the calling infrastructure is ours
   and only the panel is in Zendesk.
3. Ask how to request the **sponsored Support account** for development.
4. Confirm whether **API token Basic auth** blocks approval or is only
   discouraged, since moving to OAuth2 is a meaningful chunk of work and is
   better done before the first submission than after a rejection.
